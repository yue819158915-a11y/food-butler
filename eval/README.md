# eval —— 检索层评测

改代码之前先量基线，改完之后用同一批用例证明有没有变好。

## 快速开始

```bash
cd scut-food-agent

python eval/run.py                 # 硬约束评测（零成本、秒级）
python eval/run.py --compare       # 与基线快照对比，输出 delta
python eval/run.py --save          # 把当前结果写成新基线
python eval/run.py --gate          # CI 模式：严格违反率 >3% 退出码 1
python eval/run.py --judge         # 追加软语义 LLM 裁判（需 ZHIPU_API_KEY）
```

`--judge` 需要环境变量（不要把 Key 写进仓库）：

```bash
export ZHIPU_API_KEY=xxx          # Linux/macOS
set ZHIPU_API_KEY=xxx             # Windows cmd
$env:ZHIPU_API_KEY="xxx"          # PowerShell
```

## 当前基线（2026-11-05）

| 指标 | 基线值 | 目标 |
|---|---|---|
| 条目级违反率（严格执行用例） | **13.0%**（17/131） | ≤ 3% |
| 条目级违反率（含放宽用例） | **65.6%**（217/331） | ≤ 10% |
| 行为级断言通过 | **0/4** | 4/4 |
| 触发放宽的用例 | 5 个 | — |

行为级 0/4 的三类失败：无解时返回全库 100 条（2 例）、关键词叠加后结果数不足（1 例）、人群关键词组合后 0 结果（1 例）。

## 两层指标，为什么分开

- **条目级违反率**：返回的每一条店是否违反用户明示条件（价格/类目/地点）。这是"对/错"，必须 0 容忍。
- **行为级通过率**：系统在边界情况下的行为是否正确（无解时该不该返回 0、结果不足时该不该放宽）。这是"策略"，按用例判定 PASS/FAIL。

混成一个"综合得分"会掩盖"价格对了但人群全错"这类问题，所以分两张表。

## 用例规范

`cases.json` 里每个用例：

```json
{
  "id": "price_cap_40",
  "direction": "人均上限",
  "utterance": "人均40以下",
  "given": { "price_max": 40 },
  "must": ["price_mid <= 40"]
}
```

| 字段 | 说明 |
|---|---|
| `given` | 直接传给 `store.filter_restaurants` 的参数，**绕过 NLU** |
| `must` | 每条返回结果都必须满足的谓词列表（全满足才算合规） |
| `expect_zero` | 行为断言：无解时必须返回 0 条 |
| `expect_min` | 行为断言：结果数不得少于 N |
| `soft` | 软语义用例，不做硬断言，交给 LLM 裁判 |
| `judge_criteria` | 裁判的判定标准，越具体越稳定 |

可用谓词变量：`price_mid` / `price_min` / `price_max` / `category` / `location` / `region` / `type_raw` / `name` / `note` / `popularity`。

**写断言的红线**：必须按用户意图写，**不能复用 `store._hit_price()` 等被测实现**。否则就是拿实现验证实现，永远 100% 通过，评测等于没做。

## 为什么只测检索层

`given` 直接写死条件，不经过 `/api/chat`，好处是：
- 秒级回归、零 token 成本
- 能把**检索层的锅**和**NLU 的锅**隔开——现在「适合老人家」失效是两层都坏，混在一起测分不清该改哪

NLU 层评测（口语 → 槽位）留到 M3，需要真实 LLM 调用，结果有随机性，不适合每次回归都跑。

## 软语义裁判的校准

`--judge` 出来的分数不能直接信。先跑校准：

1. **打分**：`python eval/label.py`（逐条问，回车跳过，`q` 中途保存；每条打完即时写盘）
2. **让裁判也打一遍**：`python eval/calibrate.py --judge`
3. **看二次加权 kappa**：
   - `≥ 0.6` 可用，能当趋势指标
   - `0.4 ~ 0.6` 只能参考，不进 CI
   - `< 0.4` 裁判不可用，退回人工标注

也可以直接手改 `calibration.json`：只改 `"human": null` 为 `1~5` 的**整数**（不要加引号），`"judge"` 保持 `null`。

打分要点：**凭直觉独立打，不要猜模型会打几分**；尽量用满整个量表，12 条全打 3 分会让 kappa 失真（方差趋零时一致性系数没有意义）。

**这一步不能跳。** 不校准就直接用裁判分，测的是模型的偏好，不是推荐质量。

## 加用例的原则

新增用例前先问：**这条用例失败时，我知道该改哪一层吗？**

- 知道 → 加进 `cases.json`
- 不知道 → 说明用例写得不够具体，先把"用户这么说 / 期望 / 实际"三段写清楚

建议覆盖这五类：人均方向、类目方向、地点方向、无解边界、软语义。
